# STM32F103ZET6 BootLoader + OTA 双槽升级

让 STM32F103 的固件可以在线升级，并且**任何时刻断电都不会变砖**。

核心思路是把「下载」和「执行」彻底分开：新固件先落到外部 Flash 的槽 A，
BootLoader 校验通过后才搬进内部 Flash 执行；搬完算「试用」，
跑不起来就从槽 B 把上一版搬回来。

下载全程不碰内部 Flash —— 所以升级失败最坏的结果是「白传一次」，
现有系统毫发无损。这是架构层面的安全，不是「把窗口缩小」的优化。

---

## 特性

| 能力 | 说明 |
|---|---|
| **双槽 A/B** | W25Q128 前 1MB 划两个槽，交替存放候选固件与上一版备份 |
| **搬运后回读校验** | 搬完把内部 Flash 读回来重算 CRC —— 证明「存进去的是对的」，而不是「我收到了什么」 |
| **试用期 + 自动回滚** | 新固件须连续启动成功才转正；看门狗复位、跳转后没回来都计入失败，三次自动回滚 |
| **参数页双备份** | 两页轮转写，擦写中途掉电最多丢一次状态更新，不会丢账本 |
| **参数页自愈** | 账本被外部工具擦掉后，从两槽槽头 + 内部 Flash 实测 CRC 反推重建 |
| **版本号拦截降级** | 旧版本无法覆盖新版本，编译期开关可关（`OTA_ALLOW_DOWNGRADE`） |
| **黑匣子** | 最近 128 条关键事件落 W25Q，每次上电自动倒出最近 5 条，掉电可查 |
| **上位机** | 自带串口助手（GUI）+ 无界面命令行发送端，支持 SWD 自动复位 |

固件体积：Boot **24128 B / 32 KB（73.6%）**，App **18960 B / 480 KB**。
升级一版 17 KB 固件约 **1.5 s**（115200 / 256 B 块 / 1 ms 间隔）。

## 分区布局

### 内部 Flash（512 KB）

```
0x08000000 ┌────────────────────────┐
           │  BootLoader    32 KB   │  16 页，-Os 编到 24 KB
0x08008000 ├────────────────────────┤
           │  App 固件      476 KB  │  最多到 0x0807F7FF
0x0807F000 ├────────────────────────┤
           │  参数页 A       2 KB   │  ← 双备份，轮转写
0x0807F800 ├────────────────────────┤
           │  参数页 B       2 KB   │
0x08080000 └────────────────────────┘
```

分区只在 `flash_app.h` / `ota_param.h` 的宏里定义，其他地方一律用
`APP_ADDR` / `FLASH_END` 推导，改布局只需改这两处。

### 外部 Flash W25Q128（16 MB）

```
0x000000 ┌──────────────────┐
         │  槽 A 头部  4 KB │  32 字节有效内容，独占一个扇区
0x001000 ├──────────────────┤
         │  槽 A 数据 508 KB│
0x080000 ├──────────────────┤
         │  槽 B 头部  4 KB │
0x081000 ├──────────────────┤
         │  槽 B 数据 508 KB│
0x100000 ├──────────────────┤
         │  试用确认标记 4KB│  OtaConfirm_t，16 B
0x101000 ├──────────────────┤
         │  黑匣子     4 KB │  128 条 × 32 B
0x102000 ├──────────────────┤
         │  其余 15 MB 空闲 │  预留给历史版本 / 出厂备份
0x1000000└──────────────────┘
```

槽 B 长期保存「上一版完整固件」并带 `OTA_SLOT_FLAG_BACKUP` 标记，
它是回滚的唯一来源，所以**永远不会**被当成待安装的新固件搬走。

> **两份副本约定**：`ota_slot.c/h`、`ota_param.h`、`crc32.c/h`、`w25q.c/h`
> 在 Boot 与 App 各存一份（两个工程 `srcDirs` 互不可见）。
> **改一边必须同步另一边**，否则 App 写的头 Boot 读不懂，
> 症状只是「槽一直是 BAD」，不会报错。

## 快速开始

### 1. 编译

两个工程相互独立，分别用 EIDE（VS Code 插件）打开：

```
Boot_Loader/Boot_Loader.code-workspace
Application/Application.code-workspace
```

- 目标：`Debug`，工具链 `GCC`，优化 `-Os`
- Boot 侧必须在 **32 KB** 以内，App 侧链接脚本 `ORIGIN = 0x08008000`

工程内另有 CubeMX 生成的 `CMakeLists.txt` / `CMakePresets.json`，
当前不作为主构建流程维护。

### 2. 烧录顺序（重要）

**先烧 BootLoader，再烧 App。**

| 目标 | 地址 |
|---|---|
| BootLoader | `0x08000000` |
| Application | `0x08008000` |

只烧 Boot 会出现 `[boot] no valid app`，属正常现象（App 区还是空白）。
App 侧 `eide.yml` 的 `uploadConfigMap.OpenOCD.baseAddr` 也必须是 `0x08008000`，
漏改会按 bin 烧到旧地址。

### 3. 升级固件

**方式一：GUI 串口助手**

```bash
python Tools/SerialAssist/serial_assist.py
```

选串口 → 选 `.bin` → 勾选「新架构 FWUP」→ 填固件版本号 → 发送。
工具会自动解析日志、显示进度、用 SWD 复位让 Boot 去搬运。

**方式二：命令行（可进 CI）**

```bash
cd Tools/SerialAssist

# 新架构：直接发给运行中的 App（免手动复位，App 收完自己复位回 Boot）
python ota_headless.py app-ota Application.bin --port COM25 --ver 20

# 老协议：发给 BootLoader 的 3 秒上电窗口（App 坏掉时的救援通道）
python ota_headless.py boot-ota Application.bin --port COM25

# SWD 烧 BootLoader / 复位并抓完整上电日志
python ota_headless.py flash-boot Boot_Loader.bin --port COM25
python ota_headless.py watch --port COM25
```

> **注意**：SWD 复位后 3 秒内**不要**发新架构固件，
> 那时控制权还在 Boot，会被老协议当成裸字节流写进内部 Flash。

## 升级流程

```
        ┌──────────── 运行中的 App ────────────┐
        │ 常驻监听 USART1（IDLE 扫 'FWUP'）     │
        │ 收到固件 → 边收边写 W25Q 槽 A         │
        │ 收完 → 回读算 CRC → 对上才写槽头      │
        │ → NVIC_SystemReset()                 │
        └──────────────────┬───────────────────┘
                           ▼
        ┌──────────── BootLoader 上电 ─────────┐
        │ 读槽 A 头 → 该装吗？（版本 / 标记）   │
        │ → 把旧固件备份进槽 B                 │
        │ → 逐页搬进 0x08008000                │
        │ → 回读内部 Flash 重算 CRC            │
        │ → 写参数页 state=TRIAL,cnt=0         │
        │ → 打 COPIED 标记 → 跳转              │
        └──────────────────┬───────────────────┘
                           ▼
        ┌──────────── App 跑起来 ──────────────┐
        │ 跑满 5 s 且一直在喂狗 → 写确认标记   │
        │ 下次上电 Boot 读到标记 → 转正         │
        └──────────────────────────────────────┘

        失败路径：三次试用没等到确认 → 从槽 B 搬回上一版
```

**「头部存在」等价于「固件完整且校验通过」** —— 这是整套设计的基石。
所以顺序被严格固定为：擦数据区 → 收完 → 回读算 CRC → 才写头部。
中途任何一步失败都不写头，不会留下一个骗人的有效槽。

## 关键设计取舍

### 为什么是双槽，而不是「小心一点的单分区」

单分区升级的致命问题不是「可能失败」，而是**失败后无法自救**：
传到一半断电，旧固件已被擦、新固件还不完整，只能拿 ST-Link 救。
双槽把下载挪到外部 Flash，内部 Flash 只在「一份已经校验过的固件」面前才被改动。

### 为什么槽头独占一个 4 KB 扇区

省 4 KB 的做法是把头放在固件数据前面（偏移 0），
但那样「头已写、数据没收完」的中间态只能靠写入顺序保证，
一旦顺序被打乱就会出现「头说 100 KB、实际只有 60 KB」的自相矛盾状态。
物理隔离后，擦写固件永远碰不到头，写头也永远碰不到固件 —— 4 KB 换一个不变量。

### 为什么 CRC 要「读回来算」而不是「边收边算」

边收边算只证明「我收到了什么」，证明不了「Flash 里存的是什么」。
擦除不干净、写入被打断、电压跌落，都会让两者不一样。
只有重读才是实锤 —— 这也是唯一能挡住「写了一半但长度刚好对上」的手段。

### 为什么试用期要看「复位原因」+ 后备寄存器握手

最初的实现只看「状态=试用 且 没有确认标记」就计一次失败，
结果**连按三次复位键就把好固件回滚了** —— 它把「人按复位」和「固件死机」当成了同一件事。

现在两条依据缺一不可：

1. **`RCC->CSR` 复位标志**：只有 `IWDG/WWDG` 才算固件没撑住；
   `PIN`（人按）、`SFT`（App 收完主动回）、`POR`（插拔电源）一律不计，
   并且不写参数页（省一次 2 KB 擦写）。
2. **`BKP_DR1` 握手**：看门狗只能抓「进了主循环之后死掉」。
   固件死在时钟配置里、或 HardFault 卡在默认处理函数时狗还没开，
   板子就那么挂着。做法是跳转前写一笔，App 进 `main` 第一条语句擦掉 ——
   下次上电这笔还在，说明上次交出去的控制权根本没活过来。

> `BKP_DRx` 只有低 16 位有效。第一版用 32 位魔术字，高位被静默丢弃，
> `==` 永远不成立，整条握手失效而日志上看不出任何异常。

### 为什么参数页要两页

写参数页是「擦 2 KB 页 → 写 28 字节」，那段擦除要 20~40 ms，
而升级恰恰是最容易断电的时刻。单页时这一下掉电就变成
「有内容但 CRC 不对」，而自愈**故意不碰**这种状态（不猜），
于是 Boot 停在 OTA 等串口 —— 现场没串口就是一块砖。

双页轮转后每次只写「当前没在用的那一页」，任何时刻至少有一页完整。

## 踩坑记录（完整版见 [CHANGELOG.md](CHANGELOG.md)）

这些是只有上板才会暴露、光看代码看不出来的问题，留在这里给后来者省时间：

| 现象 | 根因 | 结论 |
|---|---|---|
| 黑匣子一条记录都没有，日志无异常 | `0x101000` 原本有残留数据，Flash 只能 1→0，首次写失败且返回值被丢弃 | 遇到无效记录要再判一次空白，非空则擦整扇区重来 |
| 连按三次复位键，好固件被回滚 | 试用计数只看「状态+无标记」，不问怎么复位的 | 必须结合复位原因；人按的不算失败 |
| 手动开 LSI 后卡死在等 `PVU/RVU` | 写 `PR/RLR` 时时钟还没路由给 IWDG | 顺序必须是 `0xCCCC → 0x5555 → PR/RLR → 等标志 → 0xAAAA` |
| 收固件时 `[app-ota] abort: timeout`，一个字节都没收 | 刷新 `last_act` 写在 `state != IDLE` 分支里，而那一次 Poll 顶部还是 IDLE | 本轮只要取到字节就无条件刷新时间戳 |
| 报 `hdr ver` 错误，但版本号没问题 | 放弃接收后残留 17 KB 数据仍在流里被扫描，固件镜像本身含 `"FWUP"` 四字节 | 一个真实故障却给出两个假方向；头部校验顺序要先算 CRC |
| 一次性擦除导致 `crc mismatch` | 5 扇区 × 45 ms = 225 ms 阻塞，DMA 环形缓冲只有 1 KB 必然溢出 | 改为惰性擦除：写之前才擦这一页 |
| `openocd flash erase_sector 0 8 8` 把 Boot 擦没了 | 索引是 2 KB **页号**，不是「第 8 个扇区」 | App 区首页 = 页 16（`0x08008000`），页 24 = `0x0800C000` |
| 参数页读出 `cnt=255`，`0/3` 永远到不了上限 | `reserved` 基底写成 `0xFFFFFF00`，把计数位也预置成 1 | 应为 `0xFFFF0000` |

## 已知限制

- **版本号需手动递增**：CRC 顶替不了版本比较（同一份源码重编一次 CRC 就变），
  所以降级拦截完全依赖上位机填的 `--ver`，填错就拦不住。
- **无固件签名**：目前只校验完整性，不校验来源。要做签名验证需同时开启
  F103 的读保护，否则密钥可从芯片读出。
- **槽 B 只保留一版**：没有历史版本管理，连续升级两次后无法回到更早的版本。
- **未附许可证**：仓库暂未声明 License（`Drivers/` 下为 ST 的 BSD-3-Clause 授权）。
